# Reflection

The notes search description explains that the input should be a short topic phrase. This matters because the search matches literal text instead of understanding the meaning of a complete question. Searching for “gradient descent” finds the sample notes, while sending a whole sentence could return nothing. The local tests confirm that capitalization does not affect the search. However, I have not completed a live comparison of different tool descriptions, so I cannot claim that changing the description improved the model's choices.

The local tests deliberately include wrong calculator input, division by zero, unsupported citations, and incorrect answers. These checks show that the program handles errors and rejects some invalid responses. One possible model mistake is using the percent symbol as a percentage operation, although Python uses it for remainder. The description tells the model to divide by 100 instead. I also added three phrasings of each test question and a ground-truth comparison. This checks whether differently worded questions produce correct answers. The recorded demonstration uses scripted replies, so actual model mistakes and consistency still need to be observed with live API tests.

If the agent could delete files or send emails, a misunderstanding could have serious consequences. I would require a preview and explicit confirmation before those actions. I would also limit which files and recipients it could access. Request and response logs would help investigate mistakes, but logging alone would not prevent damage. The current eight-step limit controls repeated calls, while the UI also avoids processing duplicate submissions again.
